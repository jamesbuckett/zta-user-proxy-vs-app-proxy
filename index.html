Who does the proxy work for?

That single question separates the two kinds of proxy. A user proxy speaks to the internet on behalf of your users. An application proxy answers the internet on behalf of your applications.

TL;DR

A user proxy sits in front of people and makes outbound requests for them. An application proxy sits in front of servers and receives inbound requests for them. Same mechanism, opposite jobs.

  • Direction. A user proxy handles traffic going out, from inside your network to the internet. An application proxy handles traffic coming in, from the internet to your servers.
  • Who is hidden. A user proxy hides the user from the website. An application proxy hides the servers from the visitor.
  • Who sets it up. A user proxy is configured by whoever manages the users' devices and network. An application proxy is configured by whoever runs the application. The other side usually never knows it is there.
  • Both at once. Many organisations run one of each: a user proxy for staff browsing out, an application proxy for customers coming in.

A proxy is a go-between: a server that receives a web request from one party, forwards it to another, and carries the answer back. The party that asks is the client (usually a browser or an app on someone's device); the party that answers is the server (the machine hosting the website or application). Every proxy sits between a client and a server, and every proxy was put there by somebody for a reason.

That somebody is the key. If the proxy was put there to serve the clients, it is a user proxy. If it was put there to serve the servers, it is an application proxy. The rest of this page is that one idea, worked through in detail: the analogies, the request flows, a side-by-side comparison, when to use which, the myths, and a short quiz to check it stuck.

Two analogies

Both proxies are go-betweens. The difference is whose side they are on.

User proxy

The personal assistant who makes your calls

Imagine you never dial a number yourself. You tell your assistant who you want to reach; they place the call, say what you asked them to say, and relay the answer back to you. The person on the other end only ever hears the assistant's voice and sees the assistant's number.

The assistant can also refuse to call certain numbers, keep a note of every call made, and, if you ask the same question twice in a day, repeat the earlier answer without dialling again.

  • You are the user, the client.
  • The assistant is the user proxy.
  • The people being called are websites on the internet.
  • The rules, the notebook and the memory are filtering, logging and caching.
Application proxy

The receptionist who takes calls for the company

Now imagine a company with one published phone number. Every call lands at reception. The receptionist checks who is calling, turns away nuisance callers, and passes each call to whichever member of staff is free and best placed to help. Callers never learn anyone's direct extension, and if one person is off sick the calls simply go to someone else.

Staff get on with their jobs knowing nobody reaches them without going through the front desk.

  • The callers are clients out on the internet.
  • The receptionist is the application proxy.
  • The staff and their extensions are the backend servers.
  • Screening, routing and the single number are authentication, load balancing and hiding the backends.
User proxy · forward proxy

How a user proxy works

A user proxy, more often called a forward proxy, sits between people and the internet. The user's device is told to send every web request to the proxy; the proxy fetches the page and hands it back. The website at the far end deals with the proxy, never with the person.

Step by step

  1. Browser to proxy. The browser hands the request to the proxy instead of connecting to the website itself. For an HTTPS site it asks the proxy to open a tunnel to that site with an HTTP CONNECT request.
  2. Proxy to website. Before dialling out, the proxy applies its rules: is this site allowed for this user, and is a fresh copy already in the cache? If the request passes, the proxy opens its own connection to the website across the internet.
  3. Website to proxy. The website answers. As far as it can tell, its visitor is the proxy: it sees the proxy's public IP address, never the employee's laptop.
  4. Proxy to browser. The proxy records the visit in its log, may keep a copy of the page in its cache, and passes the reply back to the browser. The employee sees the page as if nothing had been in between.

What each party can see

The browser sees

Only the proxy. It sends every request to proxy.corp.example and gets the pages back from it.

For an HTTPS site the browser still checks the website's real certificate through the tunnel, so it can tell if anyone is reading along, unless the organisation has set up TLS inspection (see below).

The proxy sees

Who is asking (the user and the device), which site they asked for, and, for plain HTTP or with TLS inspection, the full content of the request and the reply.

That visibility is exactly what lets it filter, log and cache.

The website sees

A connection from the proxy's public IP address. It cannot tell which person or laptop is behind it.

Some proxies announce themselves with a Via header or pass the original address along in a Forwarded header; many deliberately do not.

What about HTTPS?

Most of the web is encrypted with TLS, the protocol behind HTTPS. A user proxy cannot read an encrypted conversation just by sitting in the middle. By default it only tunnels it: the browser sends an HTTP CONNECT request naming the site, the proxy opens a connection to that site, and the encrypted bytes flow through. The proxy learns which site was visited, from the name in the CONNECT request, but not what was said.

Organisations that want to inspect content set up TLS inspection: the proxy ends the browser's encrypted session itself and starts a fresh one to the website. For the browser not to raise an alarm, the organisation installs its own certificate authority (the trusted signer behind a certificate) on every managed device. Squid calls this SSL Bump; secure web gateways call it SSL or TLS inspection.

Explicit, transparent or SOCKS?

An explicit proxy is one the device knows about: the address is set by hand, delivered by a small script called a PAC file (proxy auto-config), or pushed out by device management. A transparent proxy, also called an intercepting proxy, is one the device does not know about: the network quietly redirects web traffic to it. A SOCKS proxy is a third flavour: it relays any connection, not just web requests, without understanding what is inside.

All three are user proxies, because all three act for the client.

Application proxy · reverse proxy

How an application proxy works

An application proxy, more often called a reverse proxy (the HTTP standard also calls it a gateway), sits in front of one or more applications and receives requests on their behalf. Visitors connect to the proxy's public address; the proxy decides what to do with each request and forwards the good ones to a backend, a server that does the real work out of public view.

Step by step

  1. Customer to proxy. The public name shop.example points at the proxy, so the customer's browser connects to the proxy and completes the TLS handshake with the proxy's certificate. The browser never learns where the real servers are.
  2. Proxy to backend. The proxy decrypts the request and inspects it: web application firewall rules, rate limits and, if configured, a sign-in check. It then picks a healthy backend server, forwards the request across the private network and adds the customer's IP address in an X-Forwarded-For header.
  3. Backend to proxy. The backend server does the real work and replies to the proxy. From the server's point of view every request arrives from the proxy, which is why the header added in step 2 matters.
  4. Proxy to customer. The proxy may cache or compress the response, then encrypts it and sends it back to the customer, who only ever talked to one address: the proxy.

What each party can see

The customer sees

One public name, one address and one certificate: shop.example. Not how many servers sit behind it, where they are, or what software they run.

If a server is swapped out overnight, nothing changes for the customer.

The proxy sees

The customer's IP address and, because it holds the certificate and decrypts the traffic, the full request and response.

That is what lets it filter attacks, enforce sign-in, route by path or hostname, and cache.

The backend sees

Connections from the proxy's internal address, one after another. It learns the real client address only from a header the proxy adds, such as X-Forwarded-For or the standard Forwarded header.

It should trust that header only when the request really did come from the proxy, because anyone can type a header.

TLS termination, in one paragraph

The proxy holds the website's certificate and private key, so the customer's encrypted connection ends at the proxy. That is TLS termination. Inside, the proxy usually opens a new encrypted connection to the backend (re-encryption), or plain HTTP if the private network is trusted. A proxy can also leave the encryption untouched and route purely on the server name the client asked for, called TLS passthrough, but then it cannot read, filter or cache anything.

One name, several meanings

The phrase application proxy is used loosely across the industry. On this page it means a reverse proxy in front of applications, which is what Microsoft Entra application proxy is: a cloud reverse proxy that publishes internal web apps to the internet and makes users sign in first. You will also meet:

  • Application-layer firewalls, sometimes called proxy firewalls or application proxies: firewalls that end each connection and recreate it on the other side so they can understand the protocol inside.
  • Application gateways, such as Azure Application Gateway: a cloud load balancer with a web application firewall, which is a reverse proxy under another name.
  • API gateways, ingress controllers and service-mesh sidecars (Envoy, for example): all reverse proxies with extra jobs. A sidecar is both kinds at once, a reverse proxy for calls coming into its service and a forward proxy for calls going out.

Whatever label a vendor uses, ask the question from the top of the page: who does it work for?

When to use which

Concrete situations, with the tell-tale sign for each: look at which side of the request the problem sits on.

User proxy

You need a user proxy when

  • Staff must not reach harmful or off-limits sites. A secure web gateway blocks phishing and malware domains and enforces an acceptable-use policy on every office and remote laptop.
  • Auditors want to know who accessed what. Routing all outbound web traffic through one proxy gives a single log of every request, tied to a user name.
  • Servers need a controlled way out. Machines in a locked-down network may fetch software updates and packages only through an egress proxy with an allow-list of destinations, so a compromised server cannot call home. A classic zero-trust pattern.
  • A slow link carries the same downloads over and over. A caching proxy at a branch office, mine site or ship serves repeated updates and shared files locally.
  • You want to see exactly what your app sends. Developers point a phone or program at a local intercepting proxy such as mitmproxy, Fiddler or Burp Suite to read and replay its requests.
Application proxy

You need an application proxy when

  • Several services need one front door. One public name and one certificate, with /shop routed to one service and /api to another; nobody outside needs to know how the pieces are split.
  • The site must stay up under load. The proxy spreads traffic across a pool of servers, checks their health, and quietly drops any that fail. Adding capacity means adding a server behind the proxy.
  • Remote staff need an internal app without a VPN. An identity-aware application proxy, such as Microsoft Entra application proxy, publishes the intranet app and makes everyone sign in first. Its connector dials out, so no inbound firewall ports are opened.
  • A public app is under attack. A web application firewall and rate limiting at the proxy block injection attempts, credential stuffing and floods before they reach the application.
  • A legacy app cannot do modern HTTPS itself. The proxy handles the certificate, compression and caching in front of it, so the old application never has to change.

Both at once: one retailer, two directions

Picture a mid-sized online retailer. Its staff browse the web through a cloud secure web gateway: a user proxy that blocks malware, enforces policy and keeps an audit log. At the same time its online shop sits behind a cloud load balancer with a web application firewall: an application proxy that holds the certificate, spreads customer traffic across the shop's servers and hides them from the internet. If it also publishes its intranet HR portal to remote staff through an identity-aware proxy, that is a third proxy, again on the application side.

Same organisation, same internet, two proxies pointing in opposite directions. Staff traffic goes out along the orange path; customer traffic comes in along the blue one. Neither proxy knows the other exists, and neither needs to.

Common misconceptions

Six things people say about proxies that are not quite right.

  • A proxy is the same as a VPN.

    Not the same. A VPN (virtual private network) wraps all of a device's network traffic in an encrypted tunnel to a VPN server, whatever application produced it. A proxy works at the application level, usually just for web traffic, and does not encrypt anything by itself. Both can hide your address from the far end, which is why they get confused. Many consumer VPN apps are proxies under the hood, and modern zero-trust access services are built from proxies rather than VPNs.

  • Reverse proxies are only for load balancing.

    Load balancing is one job among many. TLS termination, a web application firewall, caching, compression, sign-in, routing by path or hostname, rate limiting, and hiding the backend layout are all reverse-proxy jobs. A reverse proxy in front of a single server is still worth having.

  • Going through a proxy makes me anonymous.

    It hides your address from the website, not your activity from the proxy. The proxy sees everything you do and usually logs it, tied to your user name. It may pass your real address on in a header. And the website can still recognise you by your login or cookies.

  • A proxy encrypts my traffic.

    Encryption is the job of TLS, not of the proxy. A user proxy normally tunnels HTTPS without touching it; with TLS inspection it actually decrypts it. A reverse proxy decrypts incoming HTTPS and may send plain HTTP to the backend. Whether a hop is encrypted depends on how it is configured, not on the word proxy.

  • If the app sits behind a reverse proxy, it is secure.

    Less exposed is not the same as secure. The proxy can block common attacks, but it does not fix bugs in the application, and it brings risks of its own: a backend that trusts an X-Forwarded-For header from anyone can be fooled, and a misconfigured proxy can leak internal addresses. Patch the app, harden the proxy, and trust forwarded headers only from the proxy.

  • Proxies only handle web pages.

    The pattern is general; the web is just where most people meet it. SOCKS proxies relay any connection without understanding what is inside, and reverse proxies such as HAProxy and Envoy forward raw connections to databases and message queues as happily as they forward web requests.

Check yourself

Five questions. Pick an answer and the explanation appears.

1/5Your IT team installs a server that every staff laptop must send its web requests through, so that gambling and malware sites can be blocked. What is it?

It acts on the users' side, handling outbound requests and filtering what they can reach. That is a user (forward) proxy, typically a secure web gateway.

2/5A public website runs on three servers, yet every visitor connects to one name and sees one certificate. What is making that possible?

A reverse proxy owns the public name, terminates TLS and spreads inbound requests across the backends. The visitor never sees the three servers.

3/5A request goes through a user proxy. What does the destination website see as the source of the connection?

The proxy opens its own connection, so the website sees the proxy's public IP address. It might still learn more from headers the proxy adds or from the user's login, so this is not anonymity.

4/5An application proxy is said to terminate TLS. What does that mean?

The encrypted connection from the client ends at the proxy. Inside, the proxy usually re-encrypts to the backend, or uses plain HTTP on a trusted private network.

5/5Who configures a user proxy, and who configures an application proxy?

Each proxy is set up by the side it works for. The other side usually never knows it is there.

Glossary

The terms this page leans on, in alphabetical order.

Application proxy
A proxy that sits in front of applications and receives inbound requests for them; a reverse proxy. Also a product name (Microsoft Entra application proxy) and, confusingly, an old name for application-layer firewalls.
Backend
A server that does an application's real work, out of public view, behind an application proxy.
Cache
A stored copy of a response, kept so the same request can be answered again without going back to the server.
Certificate authority (CA)
The trusted organisation that signs a server's certificate, the document that proves a server is who it claims to be. TLS inspection works by adding the organisation's own CA to its devices.
CONNECT
The HTTP request a browser sends to a user proxy to ask for a tunnel to an HTTPS site.
DMZ (public edge)
A network segment that faces the internet. The application proxy lives here; the backends do not.
Forward proxy
The usual name for a user proxy.
Forwarded and X-Forwarded-For
HTTP headers a proxy adds to tell the next server the original client's address. Forwarded is the standard; X-Forwarded-For came first and is still more common.
Gateway
The HTTP standard's word for a reverse proxy.
Identity-aware proxy
A reverse proxy that makes users sign in before forwarding their requests, adding authentication to applications that lack it.
Load balancing
Spreading incoming requests across several servers and routing around any that fail.
PAC file
Proxy auto-config: a small script that tells a browser which proxy to use for which address.
Reverse proxy
The usual name for an application proxy.
Secure web gateway (SWG)
A user proxy, often cloud-hosted, bundled with web filtering, malware scanning and data-loss prevention.
SOCKS
A proxy protocol that relays any connection (TCP, and UDP in version 5) without understanding the application inside.
TLS
Transport Layer Security, the encryption behind HTTPS.
TLS inspection
A user proxy decrypting and re-encrypting HTTPS so it can see the content. Needs the organisation's CA on each device.
TLS termination
A reverse proxy holding the site's certificate and decrypting incoming HTTPS at the edge.
Transparent (intercepting) proxy
A user proxy the device is not configured for; the network redirects traffic to it instead.
User proxy
A proxy that sits in front of users and makes outbound requests for them; a forward proxy.
VPN
Virtual private network: an encrypted tunnel for all of a device's network traffic to a VPN server, below the level of any single application.
Web application firewall (WAF)
A filter, usually at a reverse proxy, that blocks requests matching known attack patterns.
